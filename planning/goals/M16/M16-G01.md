# M16-G01 — Define managed coverage and the typed broker boundary

**Milestone:** M16 · **Type:** worker_goal · **Lane:** security · **Risk:** critical

**State:** not started · **Owner:** unassigned · **Execution:** local_then_separate_qualification

> Planning specification only. No application test, provider operation or feature completion is claimed.

## Outcome

Identify exactly which task inputs, outputs and runtime resources Rifare controls, and mediate them through the existing server authority.

## Dependencies

[M15-G01](../M15/M15-G01.md); [M02-G10](../M02/M02-G10.md); [M02-G19](../M02/M02-G19.md); [M15-G99](../M15/M15-G99.md)

Dependencies must be **accepted**, not merely assigned or implemented. Inspect current accepted evidence before starting.

## Bounded ownership

- Define one managed runner profile and a narrow broker protocol for permitted evidence reads, model requests, proposals and typed outputs. Keep tenant and effective authority server-resolved on every request.
- Reuse existing action schemas, exact-preview approvals, model-route bounds, credential handles, receipts, stops and reconciliation. The broker is a mediation boundary, not a second business policy engine.
- Permit only configured operation/destination combinations; do not expose a generic URL fetcher, arbitrary CONNECT tunnel, raw database connection or direct commerce adapter to the runner.
- Describe managed process, trusted broker and external-agent coverage separately. External task contexts are minimized and labeled with applicable handling obligations; API checks cannot prove external deletion or egress control.
- Treat input provenance and effective authority as memory/cache partition keys. A saved context cannot silently cross tenant/task or carry broader permissions into a restricted continuation.

Additive specification from the separately retained roadmap. Concrete assignment and allowed paths require a prior maintainer record; only M13 is assigned by ADR-0042.

## Before starting

1. Inspect the actual repository, installed workflow and accepted dependency evidence before writing code.
2. Resolve proposed module/test locations and bind the goal to existing commands; no invented executable commands or preclaimed application tests.
3. Use a dedicated worktree and isolated data/services; preserve the protected baseline and minimize sensitive evidence.
4. Read and reuse current runner, model transport, worker lease, authorization, action gateway, privacy and recovery code. The checkpoint's throwing development egress function and request-context guards are not an OS network boundary or hostile-code sandbox.
5. Assign a separate worker branch and one concrete supported Linux/container isolation profile. Bind proposed broker, isolation and restriction-state changes to actual repository paths before implementation.
6. Reuse M15's authenticated task identity where the broker is remote. Local isolation and contract work can use synthetic task identities while remote deployment remains unqualified.
7. Use synthetic protected facts, local recording endpoints and a non-production broker. No real merchant data, paid inference or production business effect is required to develop the core enforcement boundary.
8. Follow the existing focused-development workflow: at most 60 cases across four whole files and one 60-second deadline by default; one meaningful targeted fault per changed boundary. Broaden only for a concrete uncovered risk or a separately required formal gate.
9. To claim managed egress enforcement, observe the exact deployed image/runtime, network and filesystem policy, broker path, task identity and secret placement. An application-level deny function or a mocked container configuration is insufficient.
10. To claim graph restriction, exercise the supported two-branch topology, actual broker enforcement, stale in-flight work, acknowledgement failure and restart behavior. Do not generalize that result to arbitrary graphs or uncontrolled external runtimes.
11. Remote broker deployment inherits the relevant M15 live profile qualification. The current diagnostic stack and formal target-stack/security/privacy/recovery release obligations retain their original status.
12. Any optional Cloudflare gateway deployment requires its own authorized account, gateway, model route, credentials, logging/cache/billing settings and live observations. Core managed-runner completion does not require enabling or qualifying that service.
