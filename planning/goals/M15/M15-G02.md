# M15-G02 — Verify sender proof at the actual remote resource boundary

**Milestone:** M15 · **Type:** worker_goal · **Lane:** security · **Risk:** critical

**State:** remaining work · **Execution:** local_then_separate_qualification

> This packet describes outstanding work. Its presence, removal, or rendered state does not establish formal acceptance, production qualification, or executed tests.

## Outcome

Require a valid sender-bound token and a fresh proof on each supported remote request, with no bearer downgrade.

## Bounded ownership

- Use the selected library for issuer-token verification and cryptographic proof verification. Enforce trusted token confirmation, asymmetric proof algorithm, dpop+jwt type and the public proof key's thumbprint match.
- Validate the RFC 9449 method and target-URI binding, access-token hash, proof time and nonce when the selected profile requires it. Derive the effective URL from configured origin/proxy trust; ignore untrusted forwarded-host rewrites.
- Keep token audience verification distinct from proof target verification. RFC 9449 htu excludes query and fragment; existing gateway and resource validation must independently validate query parameters and request bodies.
- Place verification on the origin route, including direct access that bypasses an optional portal. Do not treat a user-agent header, portal visibility or possession of the token as sender authentication.
- Keep proof keys outside model prompts, skill files and model-generated code in the provided client. Document that external-client key custody remains the external operator's responsibility.

Additive specification from the separately retained roadmap. Concrete assignment and allowed paths require a prior maintainer record; only M13 is assigned by ADR-0042.

## Preserved acceptance criteria

- A properly bound token and proof reaches the existing permitted read/proposal path; the same token without a proof or with a different sender key is rejected before resource access.
- Wrong method, target URI, token hash, token audience, expired proof, disallowed algorithm and an untrusted proxy-origin substitution are rejected with bounded, non-secret diagnostics.
- A proof-valid request with a changed amount, query resource or proposed action still undergoes existing permission, schema, policy and exact-preview checks; sender proof grants no business approval.
