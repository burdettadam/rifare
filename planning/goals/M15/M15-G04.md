## Bounded ownership

- Extend one separately implemented client with the selected proof profile, preserving the portable task/proposal/receipt contract rather than introducing provider-specific business state.
- Support an explicitly authorized client replacement through the existing ownership and lease mechanism. Treat replacement as server-authorized continuation; do not invent an implicit OAuth token-exchange or multi-hop delegation protocol.
- If one-hop delegation is supported by the selected issuer, preserve original principal/current actor and intersect child scope and expiry with every parent ceiling. Otherwise declare further delegation unsupported and reject it.
- Minimize external task context and use task/tenant/effective-authority cache namespaces. Never transfer another client's secrets or assume an external client erased previously released data.
- Keep exact-preview approval in the existing operator/server path. An agent may prepare a proposal and inspect receipts, but cannot impersonate the approver.

Additive specification from the separately retained roadmap. Concrete assignment and allowed paths require a prior maintainer record; only M13 is assigned by ADR-0042.

## Preserved acceptance criteria

- An independent client reads the permitted synthetic case and prepares a return proposal; a separate authorized operator can review it using the existing manual flow.
- Client replacement fences the previous owner's next operation and does not extend the original expiry, add a store or restore revoked permissions.
- A requested broader or longer-lived delegated task is rejected or narrowed by the supported issuer/server contract; an unsupported delegation mechanism fails explicitly.
- The replacement client receives only its allowed case context, and the compatibility record distinguishes server-enforced scope from unobserved external-host behavior.
