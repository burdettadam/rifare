# M15-G01 — Define one remote trust profile over current task authority

**Milestone:** M15 · **Type:** worker_goal · **Lane:** security · **Risk:** critical

**State:** not started · **Owner:** unassigned · **Execution:** local_then_separate_qualification

> Planning specification only. No application test, provider operation or feature completion is claimed.

## Outcome

Specify a remote identity and sender-binding contract whose only authority comes from verified issuer claims and existing server-side task permissions.

## Dependencies

[M02-G18](../M02/M02-G18.md); [M02-G19](../M02/M02-G19.md); [M02-G99](../M02/M02-G99.md); [M07-G99](../M07/M07-G99.md)

Dependencies must be **accepted**, not merely assigned or implemented. Inspect current accepted evidence before starting.

## Bounded ownership

- Define a narrow RemoteTaskAuthenticator result containing trusted issuer and audience, original principal and current actor, sender-key thumbprint, token expiry, task ceiling and an internal server-resolved task scope.
- Configure an exact issuer, allowed signing algorithms and key sources, resource audience, canonical HTTPS origin, accepted confirmation mechanism and bounded clock/replay windows. Do not select issuer, key URL or audience from arbitrary client input.
- Map the authenticated principal to current tenant, store, customer/case and permitted operations using existing server state. Treat caller-supplied identifiers as requested resources, not evidence of membership.
- Select the RFC 9449 DPoP resource-server profile and an existing supported issuer/library integration. If the selected issuer cannot issue or confirm sender-bound tokens, leave that remote profile unavailable.
- Keep the current loopback-only opaque read grant and local worker contract explicit. A configured remote profile must never reinterpret a local grant as OAuth.

Additive specification from the separately retained roadmap. Concrete assignment and allowed paths require a prior maintainer record; only M13 is assigned by ADR-0042.
