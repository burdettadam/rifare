# M16-G04 — Demonstrate restriction across two concurrent branches

**Milestone:** M16 · **Type:** worker_goal · **Lane:** security · **Risk:** critical

**State:** not started · **Owner:** unassigned · **Execution:** local_then_separate_qualification

> Planning specification only. No application test, provider operation or feature completion is claimed.

## Outcome

Provide bounded evidence that an existing parallel branch cannot retain a removed output route when another branch admits protected data.

## Dependencies

[M16-G02](../M16/M16-G02.md); [M16-G03](../M16/M16-G03.md); [M15-G99](../M15/M15-G99.md)

Dependencies must be **accepted**, not merely assigned or implemented. Inspect current accepted evidence before starting.

## Bounded ownership

- Use a fixed two-branch task fixture: branch A requests protected case evidence while branch B holds a previously permitted export/diagnostics operation.
- Exercise the real broker and isolation profile at the admission race, with one stale authorization and one reusable/open channel. Close or reauthorize the channel before protected-data release.
- Include one missing-acknowledgement timeout and one restart at the restriction transition. Avoid expanding this goal into an arbitrary-graph scheduling or broad load framework.
- Preserve a useful permitted continuation: approved inference or a deterministic substitute, a return proposal and a typed verified-recipient update to a local recording endpoint.
- Record original principal, actor, task, lease generation, restriction version, branch and decision in minimized receipts. Do not retain protected contents or tokens merely to prove the race.
- State explicitly that an uncontrolled external agent may keep or transmit previously released information; Rifare can fence its next API operation, not revoke facts from its memory.

Additive specification from the separately retained roadmap. Concrete assignment and allowed paths require a prior maintainer record; only M13 is assigned by ADR-0042.
