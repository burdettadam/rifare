## Declared local configuration

The demonstration uses the existing TypeScript commerce modules, Node's native
test runner and SQLite fixture persistence. It uses the synthetic apparel
merchant's default profile, returns policy and existing shared support skills.
The retained focused reports identify the actual runtime executable and source
hashes. No remote model, client, delivery account or payment provider is used.

The fixture begins with case_one and resolution_case, the verified shopper/order,
an already submitted return, its synthetic native return and alpha refund, beta
credit and gamma exchange allocations. These are setup prerequisites. The new
journey uses resolution_case and compares those original IDs and baseline counts;
it does not claim to create the prior return or another case.

Email and webchat are separate verified local conversation records for that same
shopper, case and order. Partial and unavailable history remain visible. Shopper
memory remains tied to its original verified source and can be read from the
second current verified link. Channel history is not used to infer customer
identity or reconstruct unknown messages.

## Native stage and authority limits

A replacement in native created state is not physically fulfilled or delivered.
A cart in committed/active state is not a checkout, purchased order or authorized
payment. Message accepted is not customer-delivered. Refund, credit, return
authorization, physical receipt, label purchase and settlement retain their own
native owners and distinct observations. A journey reference or context digest
does not authorize any of them.

Unknown effects retain the original operation, command, approval/receipt linkage
and applicable reservations. Reopening context, changing owners, stopping model
access or losing a channel history does not authorize replay. Reconciliation uses
the actual native owner and original reference; a new source object's in-memory
counters cannot replace its persistent source ledger as the effect oracle.

The public journey projection is finite and does not require a private model
thread. Restricted callers retain the existing minimized views. Current customer
proof, exact tenant/store/case/resource bindings, source identity, current
generation, ordinary permissions, native action gates and consent still apply.
Memory, readiness, journey composition and follow-ups add no worker action grant.

## Privacy, recovery and capacity

The local G01-G04 increments retain explicit-purpose shopper memory, correction
and forgetting, all-version exact-subject selection after order reassignment,
restricted projections, current-source checks, holds, erasure and uninstall.
Guard documents contain memory ID/version rather than copied preference text.
Original native delivery copies are selected by retained identity even when the
subject no longer owns a current resource.

Dynamic follow-up retirement minimizes unheld history and revokes held personal
versions. Only provably untouched queued/pending native work can be cancelled
automatically; attempted and unknown work keeps its native handling. Restore and
import validate retained structures, replay current erasure and invalidate copied
context without resuming it. Unsuppressed held personal context causes atomic
refusal. These are logical data/lifecycle controls, not erasure of every external
copy, old backup or physical storage medium.

The existing G03 store-wide native-return and edit-child scans refuse above their
100-row capacity. G04 guard histories retain their 10,000-row bound. Native sender,
delivery, rule and guard expiry constraints remain separate. No new schema or
runtime is introduced solely for the G05 local demonstration.
