## Bounded implementation

A no-argument development command owns a new private temporary directory and its
child processes. Each fresh fixture server uses the existing commerce kernel,
customer challenge/proof owner, native synthetic cart/quote sources, preview,
receipt verifier and checkout API. Generate original ephemeral synthetic signing
keys through the existing pinned JOSE library. Do not persist raw credentials,
receipt bytes, private keys or complete verification context.

Use a private parent/child pipe for bounded synthetic bootstrap information.
The fixture child accepts only its fixed fresh/history lifecycle modes and
validated owned paths; no HTTP fixture, trust or context provisioning route is
added. The parent launches only fixed project scripts and the existing Python
client, with a minimal child environment, bounded output/deadlines and no automatic
mutation retry. It cleans only its own child handles and allocated directories.
Direct child startup without the documented parent channel must fail closed.

Fresh mode prepares synthetic preview/context pairs but leaves intent creation
and receipt capture to the independent HTTP caller. History mode opens the exact
existing native database without reseeding, issuing replacement sessions or
recreating preview/context/signing/verifier provenance. Retain the original
customer bearer only in the parent's transient memory across process restart.
Current native proof and session checks remain authoritative after restart.

The demonstration must verify original intent preparation, receipt capture,
exact retry, status and revision-bound cancellation. Kill and replace an actual
server process and prove the prior process exited. Retained receipt history must
remain readable while a previously prepared but uncaptured intent cannot acquire
new evidence with missing live owners. Two concurrent instances must have distinct
ports, data/source stores and processes, reject each other's credentials and
intent identities, and leave native commerce effects unchanged.

A bounded loopback-only lost-response probe may discard a receipt response after
the real server completed its mutation, then read the same original intent.
This is local evidence recovery, not provider outcome reconciliation. It must
not change public server behavior or introduce a proxy into ordinary client use.

Public reports contain only finite result labels, original diagnostic identifiers,
digests, process observations and qualification limits. All reported execution
flags remain false. No production endpoints, credentials, provider emulation,
merchant operation, worker, scheduler or remote delegation claim is introduced.
Separate processes are not an OS sandbox or proof of outbound isolation.
