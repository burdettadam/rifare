# M09 qualification assessment

**M09-G99 remains blocked.** The owner's instruction assigns development of all
fourteen worker goals and this assessment under ADR-0038. It does not supply the
formal M07 prerequisite, external provider evidence or a release decision.
Original planning packets and the accepted-goal ledger retain their meanings.

## Original milestone obligations

The milestone is conversion, marketing and catalog skills. Its required journey
is: create and approve a campaign, exclude an opted-out shopper, run a held-out
offer experiment and inspect its source events. Both original exit criteria are
required together:

1. Campaign previews require approval and consent checks at send time; unsafe
   discounts and unsupported checkout changes are blocked.
2. Holdout contamination and duplicate conversion attribution are detected;
   results report uncertainty and net economics.

Formal acceptance additionally requires accepted M09-G01 through G14 and M07-G99,
one current integrated candidate, its full applicable accepted regression suite,
affected connected qualifications, independent authority/security and regression
reviews, and a separate trusted milestone decision. A local development report
cannot replace those obligations. The fourteen worker records and the cumulative
checkpoint bind the actual local work and its evidence.

## Evidence scope

Development retains at most **60 actual cases across four whole files with one
60-second deadline per invocation**. The planned coherent selection contains
15 shopping, 24 marketing/measurement and 12 optional-provider cases plus the
existing nine-case privacy file. Authors commit behavioral tests before product
implementation and run no duplicate suites. Root records the actual integrated
run, and repeats only affected whole files for a concrete failure or consequential
correction. Actual totals, failures, reruns and independent dispositions belong
to the source-bound checkpoint; this assessment does not preclaim them.

The selected campaign/holdout journey is a synthetic development demonstration.
It is not the formally qualified G99 journey. New connected/partner preparation
uses distinct local IDs; original connected cases and `CASE-M09-G99-01`,
`CASE-M09-G99-02`, `CASE-M09-G99-03` remain unperformed at their stated scope.
The original TEST-034 attribution, PORT-027 leakage, PORT-026 consent and TEST-026
attachment expectations are preserved wherever local later-path cases extend
them. No old acceptance denominator, fixture or capability may be weakened.

## Blocking obligations

1. M07-G99 remains unaccepted. The acceptance ledger still contains only the four
   historical M00 development decisions. Local development of M09 cannot supply
   target-stack, real-pilot or other missing prerequisite evidence.
2. G02, G06, G07, G10, G11 and G13 require actual connected provider observations
   under approved account/API/configuration and purpose. No such evidence is
   created by local sources, fixture readiness rows or generated reports.
3. G14 requires actual authorized partner access, terms, data provenance and
   current purpose/geography/retention/deletion qualification. A fixture cannot
   authenticate these external rights.
4. The full current applicable accepted suite, original integrated qualified
   demonstration and affected connected qualification have not been performed as
   an M09 acceptance campaign. A blocked assessment does not start that campaign.
5. Final local reviews and the maintainer's nonrelease integration decision cover
   their explicitly bounded development scope. Formal milestone acceptance
   requires its own current evidence and trusted decision.

Optional capabilities remain explicitly optional and default-disabled. Their
unavailability is visible; it is neither a passing feature nor a silently
approved release exclusion. No external message, payment, production operation,
provider contact, hosted push, publication, tag or release is part of this work.
M10 remains unassigned.
